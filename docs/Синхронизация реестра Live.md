## Канонический журнал публикаций

- `.github/live-selected-events.json` — неизменённая историческая часть.
- `.github/live-publications/<snapshot_id>.json` — маленькая неизменяемая запись каждого действительно подготовленного к выдаче/показанного финального списка. Только выбранные матчи, никогда не весь Top-30 и не все технические кандидаты снимка.
- Обе части читаются вместе. Наличие записи в main сразу исключает её event_id при full; переписывать или материализовать большой исторический JSON не требуется. Прямой refresh разрешён по прежним правилам.
- Каждый файл содержит версию схемы, snapshot_id, исходную отметку времени и полные технические selection-записи с причинами, исходными условиями и спортивным рангом. Спортивный алгоритм v8 не изменён.

## Обязательный порядок фиксации

1. Сформировать окончательный короткий список. Не создавать запись автоматически по `sports_ready`: технический выбор ещё не означает публикацию в чате.
2. Подготовить JSON выбора с `selected_at_utc` и массивом `selections` (`event_id`, `sports_reason`, `expected_scenario`) только для фактического финала.
3. Выполнить прежнюю команду `python3 scripts/live_selection.py --snapshot snapshots/live/<ID>.json --choices <choices.json>`. Она читает объединённую историю и создаёт небольшой файл `.github/live-publications/<ID>.json`, не переписывая большой JSON. `--receipt-directory` нужен только для изолированных проверок, не для подмены канонического пути.
4. Записать этот маленький файл в **main** через GitHub `create_file` (одна операция), либо обычный git-коммит/push при доступной авторизации. При создании через git не перезаписывать параллельные изменения main. Если файл уже существует, сверить его содержимое и считать идемпотентным только точное совпадение; отличающуюся запись не заменять.
5. Успешная запись в main — признак сохранения в каноническом реестре. Вывод скрипта `local_only_until_committed_to_main` не означает синхронизацию. Подготовленный локальный файл не объявлять сохранённым в GitHub.

Публикация короткого финала не должна задерживаться ради длительной фиксации. Короткая запись перед final допустима, когда список уже окончательно сформирован и операция занимает считанные секунды. Если отправка не удалась, честно отметить это в финале; локальный файл нужно восстановить в main до следующего full. Не придумывать точное время, когда пользователь прочитал ответ: отметка реестра не доказывает время доставки или фактический вход.

## Безопасность целостности

`read_selected_events` объединяет ID исторического файла и отдельных записей. Повреждённая запись не игнорируется: full останавливается с явной ошибкой вместо выдачи возможных дублей. То же относится к отсутствующему/повреждённому историческому файлу. `merge_publications` предоставляет объединённые полные записи для анализа и новых публикаций, сохраняя исторические объекты. Повторная запись того же выбора идемпотентна; изменение существующего выбора запрещено.

Никаких API-запросов, расписаний, фонового мониторинга, новых Live или обновления Excel этот механизм не добавляет. Архив снимков не является журналом опубликованных выборов. Нельзя исключать все события из сохранённого снимка.
