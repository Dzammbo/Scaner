# LIVE: дневная четвёрка групп и четыре строки на матч

Согласовано 28.10.2026. Ручной LIVE использует `live-daily-pockets-20261028-v2`, формат `live-four-lines-20261028-v2`. Этот документ имеет приоритет над прежними инструкциями о спортивной пятёрке, одной длинной строке, справочных линиях после выдачи, обязательном показе ГП/Г1/Г2/Г3 и альтернативном тотале в коротком Live. Исторический v8 сохраняется для исследовательских серий и старых снимков.

## Группы на день

Каждый день в 06:00 Europe/Moscow задача ChatGPT «Статистика Scaner и группы Live» запускает штатную команду «статистика» в том же чате. После успешного полного пересчёта выводит общую таблицу, затем фиксирует до четырёх действующих карманов из всех семейств: N>30 и ROI без трёх лучших >0. Контрольная пятёрка и широкий пул исключены. Приоритет: неокруглённый ROI без трёх по убыванию, затем N по убыванию, затем стабильный section/pocket_id. Малые/минусовые группы не заполняют нехватку.

Канонический текущий набор: `.github/live-daily-pockets.json`. Неизменяемый дневной архив: `.github/live-daily-pockets/YYYY-MM-DD.json`. Сохранить исходный report_path, generated_at, дату решения, ранги, идентификаторы, N/ROI/ROI без трёх и SHA256 каталогов. Дневной файл и указатель коммитить в main вместе. Четвёрка неизменна до следующей успешной утренней фиксации: ручная «статистика», очередной LIVE и обновления сборщика её не меняют. При ошибке утренней задачи не подменять новый результат старым; предыдущий набор сохраняется с отметкой об отсутствии новой фиксации. Существующий набор на дату не переписывать повторным запуском. Архив и указатель от 28.10.2026 содержат прежнюю пятёрку: они остаются неизменными, а действующий Live с момента изменения использует только ранги №1–4. Группа №5 из сегодняшнего архива не участвует в отборе; с 29.10 новые дневные файлы содержат не более четырёх групп.

Для формирования после загрузки полного свежего JSON использовать проверяемый код:

```bash
python3 scripts/live_daily.py --freeze-report /path/to/report.json --report-path research/live-results-refresh/YYYY-MM-DD/RUN-1.json --date YYYY-MM-DD
```

Команда проверяет полноту отчёта, действующие каталоги и дату, создаёт дневной файл и обновляет указатель локально. Сохранение считается выполненным только после коммита обоих файлов в main. Если среды Python нет, воспроизвести тот же алгоритм по исходному JSON без округления, проверить ID/хэши по каталогам и атомарно сохранить оба JSON через GitHub. Не определять ранг по округлённой Markdown-таблице.

На 27.10.2026 стартовый набор сформирован из последней вызванной пользователем статистики: `research/live-results-refresh/2026-10-27/40483708664-1.json`, срез 12:52 МСК. Первый автоматический запуск назначен на 28.10.2026 06:00 МСК.

## Отбор

Сначала группа №1 заполняет доступные места, затем №2 и далее до №4. Максимум пять уникальных матчей; одна группа может занять все пять. При нехватке выдаётся меньше пяти, пятая группа не используется. Матч нескольких групп относится к первой по приоритету. Внутри группы порядок по прежним признакам свежей угрозы: класс/окно, створы, завершения, двусторонние завершения, опасные атаки, сопоставимый профиль, стабильный ID.

Каждый карман проверяется исходным модулем, который ведёт его статистику: distinct/independent/refined/seven_direction/external. Сильный допуск сохраняется там, где входит в определение группы; на широкий карман 2:0/0:2 общий strong-фильтр не накладывается. Используются точные основная FT-линия и её коэффициент до отбора. Без исполнимой актуальной котировки место не заполняется. Четвертной тотал сохраняется точно, пониженную альтернативу в короткой карточке не показывать.

Окно поиска 5-89 минут с индивидуальными границами каталога. Дешёвые условия четырёх действующих дневных групп проверяются для всей доски; каждый потенциальный кандидат затем получает собственные запросы динамики и точной линии. Произвольного ограничения Top-30 у ручного LIVE нет. Потолок одного запуска 3000 фактических API-вызовов, параллельность 16, по заголовку провайдера сохраняется резерв 200 запросов от часовой квоты. Кандидаты упорядочены по рангу дневной группы и предварительной игровой оценке. Если доступной часовой квоты не хватает, явно показывать число проверенных и непроверенных; непроверенные события не объявлять неподходящими. Точный набор и спортивное ранжирование не упрощать ради скорости. Фоновый сбор имеет отдельный потолок 160 запросов каждые пять минут, чтобы оставить квоту для ручного LIVE; это может уменьшить глубину фонового сбора, но не меняет старые входы или расчёт ROI. Новых сторонних источников нет.

Для ожидания 3/5 минут и переходов счёта используются ранее сохранённые ручные LIVE-снимки этого режима за последние два часа. При отсутствии необходимого предыдущего наблюдения вход не придумывается. Триггеры сохраняются, но исследовательский seen не наследуется: события, отобранные исследовательским сборщиком, остаются доступны для первого показа пользователю. Из full исключаются только фактически опубликованные события, повтор - по явному refresh.

Ручной CLI `scripts/live_snapshot.py` вызывает `live_daily.collect`, возвращает готовые `live_markdown`, `response_format`, `daily_pockets`, `daily_group` и точные цены. Строка `LIVE_MARKDOWN_JSON` содержит готовую выдачу. Она печатается первой и немедленно читается из потока лога; её появление - момент ответа пользователю. Для мобильного клиента продублировать карточки в финальном ответе сразу после одной быстрой записи опубликованных ID через GitHub `create_file`: промежуточное сообщение может отобразиться позже. После строки `LIVE_MARKDOWN_JSON` не выполнять дополнительный разбор огромного JSON, получение нового снимка, проверку истории или многократные GitHub-коммиты перед финальным ответом. Для записи брать только `display_event_ids` и нужные поля выбранных матчей из короткой строки `LIVE_SELECTION_JSON`, которая содержит только показанные матчи; заранее известный путь `.github/live-publications/<snapshot_id>.json` создавать одним вызовом. Если запись временно не удалась, сразу выдать карточки с явным статусом записи и повторить фиксацию отдельно. Время от готового вывода до финального ответа контролировать по UTC-меткам лога и ответа. Большой `LIVE_SNAPSHOT_JSON` в этом режиме больше не пишется в лог; полный снимок сохраняется в `snapshots/live` после выдачи. Не ждать завершения workflow или сохранения снимка в GitHub. Действительно показанные матчи фиксировать в реестре после вывода; если вывод не состоялся, публикацию не записывать. Порядок: свежий снимок -> готовые карточки -> немедленная выдача -> фоновое сохранение и фиксация. Дополнительный этап получения цен пропускается. Функция старого `collect()` оставлена для замороженного исследовательского режима; её правила, версия и данные не меняются.

## Согласованный вывод

Один короткий заголовок. Каждый матч - ровно четыре строки. Названия лиг и команд писать по-русски: для известных имён - установленная русская форма, для остальных - читаемая транскрипция латинского имени провайдера. Не оставлять английские названия, не переводить логику и не подменять ID исходного события. Отображение выполняет `scripts/live_ru.py`. Пример условный:

**Live · 13:20 МСК · 1/5**

**1. Португалия, Примейра · Команда А - Команда Б · 53′ · 2:0**\
**ТБ 3,5 × 1,90**\
За 5′: удары 3:2, створы 1:1; xG н/д; удалений нет.\
**Группа №1: «45-59 минут, 2:0 или 0:2».**

В третьей строке только доступная краткая характеристика и существенные пробелы: реальная длительность свежего интервала, удары/створы, xG, удаления. Неизвестное не заменять нулём; устаревшую динамику не показывать как свежую. В четвёртой - ранг группы на день и её название. Приоритеты всех пяти групп, воронку, исторические профили, ROI группы и длинные обоснования в обычном LIVE не выводить. Развёрнутые сведения - только по отдельному запросу. В ответе ассистента остаётся финальная строка «Уверенность: XX/100».

Фактически показанные выборы фиксировать прежним `scripts/live_selection.py` и маленьким `.github/live-publications/<snapshot_id>.json`. Новая запись сохраняет неизменённый дневной архив, действующие группы, группу матча, её ранг и версию формата. Исторические публикации и исследовательские журналы не переписывать. Снимок сам по себе публикацией не является.
