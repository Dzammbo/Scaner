# Scaner

## Канон ручной команды «сканер»

При пользовательском вызове команды «сканер»:

1. Запускать свежий Scanner тем же hot-path, который используется в текущем ручном режиме.
2. Выдавать результат пользователю таблицей.
3. Вся пользовательская таблица должна быть полностью на русском языке:
   - русские заголовки столбцов;
   - названия видов спорта и турниров по-русски, если для них есть однозначный русский эквивалент;
   - формулировка ставки по-русски;
   - имена игроков/команд не транслитерировать искусственно, если это официальные собственные имена.
4. В пользовательской таблице не выводить столбцы `strategy_id`, «Стратегия» и `tier`.
5. В пользовательской таблице показывать только сигналы с текущим коэффициентом от 1.39 до 6.00 включительно.
   - Нижний и верхний пороги относятся только к пользовательскому выводу команды «сканер».
   - Сигналы с коэффициентом выше 6.00 не показывать пользователю, но продолжать фиксировать в forward-log для последующего settlement и статистики.
   - Сигналы с коэффициентом ниже 1.39 также не показывать пользователю, но forward-log и статистику из-за этого не менять.
6. Для тенниса применять терминальный фильтр уже на уровне Scanner:
   - не выдавать ставку на игрока, если соперник уже выиграл как минимум один сет и в текущем незавершённом сете ведёт 5+ геймов при счёте выбранного игрока 0-2 и отрыве не менее 3 геймов;
   - типовые состояния для отсечения: 0:5, 1:5, 2:5 в сете, который может закрыть матч;
   - цель фильтра - убрать практически терминальные live-состояния вроде 5:1 в решающем сете, а не заменить стратегию общим ограничением по коэффициенту.
7. Базовые столбцы пользовательской таблицы: «Вид спорта», «Турнир», «Матч / счёт», «Ставка», «Коэффициент».
8. Показывать только основные версии стратегий. Reverse/counterfactual и отдельные зеркальные исследовательские ветки в пользовательскую таблицу команды «сканер» не выводить.
   - Reverse продолжает сохраняться в forward-log, settlement и статистике.
   - Если у стратегии есть отдельная зеркальная исследовательская версия, помеченная `user_output=false`, она не показывается пользователю как самостоятельная ставка.
   - Пользовательская таблица должна однозначно отвечать, какая сторона является основной ставкой по стратегии.
9. Не менять стратегии, фильтры Scanner или правила forward-log автоматически из-за требований к формату пользовательского вывода, кроме явно согласованных правил выше.


## Канон reverse-анализа

1. Для каждой бинарной стратегии Scanner параллельно сохраняет counterfactual reverse-ставку на противоположную сторону при том же состоянии матча.
2. Для reverse обязательно фиксировать реальный коэффициент противоположной стороны в момент исходного сигнала. Нельзя считать reverse ROI по исходному коэффициенту.
3. Основная стратегия и reverse рассматриваются раздельно: исходный сигнал продолжает жить по своей логике, reverse используется как независимая исследовательская ветка.
4. В settlement по каждой стратегии считать одновременно:
   - W/L/PUSH основной стороны;
   - profit и ROI основной стороны;
   - W/L/PUSH reverse;
   - profit и ROI reverse.
5. Для старых сигналов, где reverse-коэффициент не был сохранён, допустимо считать только reverse W/L как counterfactual outcome. ROI по ним не считать и не реконструировать приблизительно без фактической цены.
6. Никакую стратегию автоматически не переворачивать и не отключать только из-за короткой серии. Решение принимается после накопления достаточной выборки и проверки устойчивости результата.


## Пользовательское именование стратегий

1. В пользовательском чате не показывать технические идентификаторы стратегий вида `Sxx`, `Txx` и аналогичные внутренние коды.
2. Все стратегии, reverse-стратегии и результаты по ним в чате называть только понятными русскими названиями.
3. Технические идентификаторы сохранять только для архитектуры, кода, логов, forward-log, settlement, отладки и внутренних таблиц.
4. Если в источнике или расчёте стратегия доступна только по техническому ID, перед выводом пользователю сопоставить её с русским названием из канонического реестра стратегий.
5. Это правило распространяется на таблицы, сводки, статистику, сравнение основной и reverse-стратегии и любые пояснения пользователю.


## Канон квоты BetsAPI

1. Проверенный provider-limit BetsAPI: 1800 запросов в час.
2. Рабочий общий потолок: 1750 запросов в час. Последние 50 запросов/час остаются аварийным запасом.
3. Scanner получает до 600 запросов в час.
4. Автоматический Scanner запускается каждые 5 минут.
5. Один проход Scanner может использовать максимум 50 запросов, включая 2 live-board запроса; detail-бюджет одного прохода - максимум 48.
6. Лимит 600/час считается rolling-window и включает автоматические и ручные проходы. При исчерпании бюджета проход фиксируется как пропущенный по квоте без сетевых вызовов.
7. Mining получает отдельный потолок 1150 запросов в час.
8. Утреннее эксклюзивное окно Интуиции 06:59-10:00 МСК имеет приоритет над обычными Mining-процессами; его канонические правила не менять из Scanner.
9. Если фактические provider headers показывают меньший доступный остаток, они имеют приоритет над локальными бюджетами.


## Стратегия «Фора гостей после первого гола при 0:1»

- Футбол, live.
- Триггер: первый гол матча делает счёт 0:1.
- Окно входа: 0-5 минут после первого гола.
- Вход: текущая главная азиатская фора гостей из live-линии.
- Линия заранее не фиксируется. Scanner принимает любую main AH, которую рынок считает основной в момент сигнала.
- В forward-log сохраняются фактическая фора гостей, её коэффициент, минута, счёт, противоположная фора хозяев и её коэффициент.
- Reverse считается по фактической противоположной стороне при той же линии.
- Пользовательский вывод показывает точную пришедшую фору.
- Исходная forward-статистика при добавлении: 18 ставок, 17 побед, 1 поражение, ROI +81,1%, средний коэффициент 1,915. Это стартовое исследовательское основание, а не гарантия будущего результата.


## Очистка оперативного Scanner

С 2026-09-26 из оперативного 5-минутного Scanner выведены и перенесены в Mining:
- «Гол после 85-й при коэффициенте 4.00+» - на момент решения 30 рассчитанных ставок, 2 победы / 28 поражений, ROI -66,5%.
- «Зеркало разгромного сета - за проигравшего предыдущего сета» - 16 рассчитанных ставок, ROI -32,5%.
- «Зеркало плотного сета - за проигравшего предыдущего сета» - 17 рассчитанных ставок, ROI -42,7%.

Правило переноса:
- накопленный forward-log не удалять;
- settlement и историческую статистику сохранять;
- дальнейшее исследование, reverse и повторную валидацию вести в Mining;
- исключённые стратегии не должны потреблять detail-budget оперативного Scanner;
- возврат стратегии в Scanner только отдельным явным решением после новых данных.


## Core 8 оперативного Scanner

С 2026-09-27 оперативный Scanner после аудита ограничен шестью точечными стратегиями:

1. «Гол после 60-й при счёте 0:1» - Mining P1, первая доступная точка 60-69, один вход, без фильтра коэффициента и времени первого гола.
2. «За победителя предыдущего плотного сета».
3. «Рыночный основной тотал больше при счёте 1:1».
4. «Против live-фаворита при равном первом сете».
5. «Решающий сет - за победителя второго сета».
6. «Гол после 70-й при счёте 0:2 и коэффициенте 1,80-1,99».

Все остальные стратегии:
- не удаляются из реестра и истории;
- не потребляют detail-budget оперативного Scanner;
- продолжают исследоваться и накапливаться в Mining;
- могут быть возвращены в Core Scanner только отдельным явным решением на основании новых данных.

Цель Core 8 - не широкий mining universe, а частая и максимально полная проверка заранее выбранных точечных состояний.


## Канон coverage и эпох forward-теста

1. Исторические результаты Scanner до перехода на Core 8 и stateful pre-filter считать exploratory-эпохой.
   - W/L/PUSH, profit и ROI по реально записанным ставкам остаются фактическими.
   - Эти результаты не считать репрезентативными для полного потока стратегии, если Scanner физически не проверял всех кандидатов.
   - Не использовать старую неполную выборку как окончательное доказательство наличия или отсутствия edge.

2. Clean forward-эпоха начинается после внедрения Core 8 и stateful pre-filter 2026-09-26.
   - Статистику clean forward считать отдельно от exploratory.
   - Не смешивать две эпохи при оценке воспроизводимости стратегии.

3. Для каждой стратегии Core 8 обязательно считать coverage:
   - eligible candidates - все события, которые прошли канонический дешёвый pre-filter стратегии;
   - checked candidates - eligible events, для которых фактически получен необходимый detail/market quote;
   - coverage = checked candidates / eligible candidates.

4. Полноценной forward-выборкой считать стратегию только при coverage >=95%.
   - При coverage <95% W/L/ROI показывать вместе с явной пометкой о неполной выборке.
   - Низкий coverage является риском selection bias и ограничивает выводы по стратегии.

5. Forward-отчёт по стратегии должен включать минимум:
   - N рассчитанных ставок;
   - W/L/PUSH;
   - profit;
   - ROI;
   - eligible candidates;
   - checked candidates;
   - coverage;
   - эпоху: exploratory или clean forward.

6. Исключённые из Core 8 стратегии не считать окончательно опровергнутыми только по старой неполной Scanner-выборке. Их дальнейшая полная проверка ведётся в Mining.


### Аудит settlement 2026-09-27

- Live Asian Handicap: settlement считается по голам после момента ставки; старый расчёт по полному финальному счёту признан ошибочным и не используется.
- Live Goal Line: settlement считается по полному финальному тоталу матча, включая голы до ставки.
- Теннис Match Winner: settlement только для завершённых матчей; retirement/abandoned не превращаются автоматически в W/L.
- S20 до 2026-09-27T19:42:00Z считать exploratory mixed sample: evaluator смешивал current_goals+1.0 и fallback main Goal Line.
- С 2026-09-27T19:42:00Z S20 = только фактический рыночный main Goal Line при счёте 1:1, отдельная clean-forward эпоха.
- Forward-log дедуплицирует реальную ставку по event_id + exact_bet_line, но обязан хранить все strategy_ids, которым эта ставка соответствует.

- первая доступная точка Scanner в интервале 60-69 минут при счёте 0:1;
