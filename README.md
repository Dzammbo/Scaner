# Анализ предложений беттеров и дневник исходов

## Назначение репозитория

Этот репозиторий используется исключительно для:

1. независимого анализа спортивных исходов, предложенных беттерами;
2. ведения «Дневника исходов»;
3. расчёта и анализа всех записей дневника, включая общую статистику и разрезы;
4. ручного отбора футбольных матчей на ТБ по согласованным прематчевым и live-сценариям без балльных порогов;
5. ручного анализа конкретных матчей по рынку ТМ 1,5 жёлтых карточек в первом тайме на основе отдельной исследовательской памятки.

Любые прежние задачи автоматического Scanner, Mining, S30, live-сигналов, forward-тестов и исследования автоматических стратегий исключены из активного `main`.

## Источник истины

- Каноническая ветка: `main`.
- Канонический дневник исходов пользователя: `Дневник исходов/Дневник исходов.xlsx`.
- Отдельный дневник прогнозов Джарвиса: `Live ТБ/Live ТБ.xlsx`. Текущий режим содержит один «Основной» спортивный выбор на матч с отдельным заключением по линии; исторические контуры «Оптимальный» и «Агрессивный» сохранены без пересмотра.
- Правила анализа беттеров: `docs/Канон анализа предложений беттеров.md`.
- Правила ведения и анализа дневника: `docs/Канон дневника и анализа записей.md`.
- Правила отбора футбольных ТБ: `docs/Канон отбора футбольных матчей на ТБ.md`.
- Исследовательская памятка по ЖК первого тайма: `docs/Памятка по ЖК первого тайма.md`.

Копия дневника в ChatGPT Library используется как рабочая пользовательская версия. После каждого изменения дневника версии в репозитории и Library должны быть синхронизированы. При расхождении сначала проверить дату и версию; без подтверждения не объединять данные автоматически.

## Команды

### «Оцени»

Провести независимый анализ каждого предложенного исхода по канону. Не принимать мнение беттера за исходную гипотезу. Сначала оценить спортивную составляющую, затем цену и альтернативы.

### «Добавь в дневник»

Внести новую запись в канонический дневник. Сначала проверить номер, дату, турнир, матч, рынок, коэффициент, сумму, тип Live/прематч и статус. При критичной неоднозначности запросить уточнение.

### «Обнови дневник» / «Рассчитай результаты»

Проверить незакрытые записи, внести фактические результаты и пересчитать связанные итоги. Не изменять исходные условия записи задним числом.

### «Проанализируй дневник»

Провести анализ всей актуальной выборки или указанного периода. Разделять факты, расчёты и выводы. Показывать размер выборки и не выдавать малые разрезы за устойчивую закономерность.

### «Найди верховые матчи» / «Проведи полный анализ по гипотезам»

Применить канон отбора футбольных матчей на ТБ к широкому списку или конкретному матчу по названию, ссылке или скриншоту. Объяснить голевой сценарий, аргументы против и полноту данных. Отдельно оценить конкретную линию и цену до матча либо условия повторной проверки в live. Баллы, обязательное совпадение всех признаков и закрытый прематчевый список не использовать. Результаты выдавать текстом в чате. Фоновое наблюдение и автоматические сигналы эта команда не запускает.

### «ЖК» / «ЖК: <матч>»

Разобрать конкретный футбольный матч по рынку ТМ 1,5 жёлтых карточек в первом тайме согласно `docs/Памятка по ЖК первого тайма.md`. Проверить свежие командные данные, турнирный карман, судью, силу команд, контекст и точную цену. Не переносить историческую частоту лиги автоматически на доступную букмекерскую линию: учитывать выборочную доступность рынка. Выдать одно заключение: ПОДХОДИТ, ПОГРАНИЧНО или НЕ ПОДХОДИТ. Если коэффициент не указан, оценивать только спортивную пригодность без финансового заключения.

### «live»

**Жёсткий порядок выдачи:** как только из лога получена и разобрана строка `LIVE_SNAPSHOT_JSON`, немедленно отправить пользователю отдельным видимым сообщением в чат воронку и готовые матчи. До этого сообщения запрещены refresh, внешний поиск, проверка сохранения истории, запись `.github/live-selected-events.json`, работа с дневником и любые другие tool-вызовы. После первичной выдачи продолжить уточнение и техническую фиксацию параллельно и при необходимости дать короткое дополнение. Эти операции не задерживают и не отменяют уже готовый первичный ответ. Время `selected_at_utc` брать по фактической публикации пользователю, а не по моменту внутреннего решения.


Получить свежий снимок доступных футбольных матчей через BetsAPI Events API и применить воспроизводимый спортивный отбор. Предварительный Top-30 и финальный Top-10 формируются кодом исключительно по спортивным признакам. Линия и коэффициент не участвуют ни в порядке, ни в допуске. Для каждого выбранного кандидата показать страну, лигу и команды по-русски, минуту, счёт, спортивные основания и, только справочно, основную линию Events, коэффициент и число дополнительных голов для полного выигрыша. Не оценивать конкретный тотал и не предлагать альтернативную линию: её выбирает пользователь по доступному рынку.

Events API используется для общего списка, минуты, счёта, накопленной статистики и одной свежей основной линии тотала матча. После спортивного прохода по всему пулу максимум 30 кандидатов одновременно получают `event/stats_trend` и основную линию Events (`odds_market=3`). Динамика рассчитывается только для подтверждённых интервалов; пропуски не заменяются нулями. Коэффициенты всего пула заранее не запрашиваются. Полный Bet365 API и альтернативные линии в текущем процессе не используются. Высота основной линии и требуемое число голов являются справочной информацией и не меняют спортивный список.

В начале ответа обязательно показывать воронку снимка: **всего матчей в live-окне / допущено к содержательному анализу / обогащено поминутной динамикой / выбрано спортивным Top-10**. Рабочее окно автоматической команды: **8-60-я минута включительно**. Женский, молодёжный, юниорский и резервный футбол не исключать; категорию каждого матча обозначать отдельно. Конкретный матч после 60-й минуты анализировать только по отдельному запросу пользователя. Общий спортивный пул не обрезается по числу матчей. Ограничены только дополнительные запросы: максимум 30 событий, всего до 61 API-запроса за full-проход. Итоговый список содержит до 10 воспроизводимо подтверждённых матчей без искусственного добора.

Если подходящих матчей нет, ответить «Подходящих матчей нет» и показать только краткую числовую воронку, при необходимости время снимка/сбора. Матчи, названия команд, линии, коэффициенты и карточки «ПРОПУСК»/«НАБЛЮДАТЬ» в таком ответе не выводить. Пропущенные матчи в обычной выдаче live не показывать; объяснять их только по прямому запросу. Это правило оформления, критерии анализа и охват остаются прежними.

Показать быстрый текст с максимум десятью спортивными кандидатами и справочной основной линией Events без заключения по тоталу. Один матч показывается в основном топе только один раз: его ID и неизменяемая спортивная запись со снимком и версией правил фиксируются в `.github/live-selected-events.json` через `scripts/live_selection.py` и исключается из последующих обычных full-проходов. Повторный разбор допускается только по прямому запросу пользователя через refresh. С 14.10.2026 live не читает и не обновляет Excel, не проверяет прежние результаты и не синхронизирует дневник. Сохранение API-снимка для динамики остаётся автоматическим. Постоянного фонового наблюдения нет.

### «Обнови дневник live»

По отдельной команде пакетно обновить `Live ТБ/Live ТБ.xlsx`: перенести ещё не внесённые показанные спортивные выборы и рассчитать долю матчей минимум с одним и минимум с двумя последующими голами. Новая версия не содержит рекомендованного тотала и не образует финансовый ROI прогнозов Джарвиса. Исторические строки и их финансовые расчёты не изменять. Фактические выбранные пользователем линии и цены учитывать только в основном `Дневнике исходов.xlsx`. Брать предложения из ответов в чате и технического массива `selections`, сверять исходные условия со снимками и проверять дубли.

Основной `Дневник исходов/Дневник исходов.xlsx` вести отдельно только по фактическим выборам пользователя; его не менять при обновлении Live ТБ. Исторические контуры сравнивать отдельно от текущего режима «Основной». Исторические 53 live-прогноза и исходный итоговый отчёт за 13.10.2026 сохранены; отдельный дневник прематча не восстанавливается.

### Уточнение быстрого live от 15.10.2026

Первичный ответ остаётся быстрым: один общий API-снимок, предварительный список максимум из 30 событий, параллельное получение их `event/stats_trend` и основной линии и до десяти воспроизводимо подтверждённых спортивных кандидатов. Внешний поиск не обязателен: после первичного ответа проверяются максимум 1-3 матча с конкретным существенным сомнением, параллельно, с общим бюджетом 20-30 секунд. Перед дополнением обязательно обновляются счёт и активные линии только этих матчей. При задержке свежие данные не подменяются старыми.

Снимки каждого вызова сохраняются в `snapshots/live/`; повторные матчи дополнительно получают динамику за фактический интервал между снимками. Основная свежая динамика предварительных кандидатов берётся из поминутного `event/stats_trend`, поэтому она может быть доступна и при первом снимке события при достаточной полноте ряда. Пропуски и исправления счётчиков не превращаются в нули или ложные изменения. Сохранение истории не блокирует первый ответ; работа с дневником выполняется только отдельной командой.

Запуск: workflow_dispatch либо свежий `.github/live-request.json` (`full` или `refresh`, для refresh максимум три ID). Сбор не запускается от обычных изменений кода/дневника и не работает по расписанию. Подробности, ограничения и порядок проверки эффективности закреплены в каноне отбора ТБ.

### Реализация sports-only-2026-10-15-v5

До 30 кандидатов получают динамику и основную линию одним параллельным этапом, максимум 16 запросов одновременно и 61 запрос за full-проход. Если кандидатов меньше 30, обогащаются все доступные без добора. После обогащения код формирует итоговый спортивный Top-10 без промежуточного ручного сужения. Статистика всего исходного пула остаётся доступной.

Каждая команда live самостоятельна: предварительный Top-30 зависит только от текущего общего снимка. Очереди учитывают интенсивность ударов, доступный xG, опасные атаки, угловые, активность обеих команд и двустороннее давление. Внутри очередей чередуются темп на игровую минуту и накопленный объём. Опасные атаки являются самостоятельным опережающим маршрутом, а не фоновым показателем. Двустороннюю угрозу отражает активность менее активной стороны.

После обогащения метод `fresh_sports_routes_v1` воспроизводимо чередует три маршрута: свежие качественные моменты, устойчивое опасное давление с подтверждением ударами/угловыми и свежую двустороннюю угрозу. Окна 5/10/15 минут используются из уже полученного `stats_trend`; дополнительных API-запросов нет. Список ограничен десятью матчами и не заполняется искусственно. Основная линия, коэффициент и число требуемых голов не участвуют в этом решении.

Последнее состояние рынка не подменяется старой котировкой. Время изменения цены и время проверки рынка учитываются отдельно. Данные перед перерывом, частичные интервалы и непроверенная актуальность обозначаются явно. Владение не выдаётся за статистику отдельного 10-минутного периода.

Фиксация реально показанного Top-10: `python3 scripts/live_selection.py --snapshot snapshots/live/<ID>.json --choices <файл выбора>.json`. Новый технический выбор хранит спортивное основание и сценарий, но не рекомендацию тотала. Исторические записи с линиями сохраняются без изменения.

Проверки без API: `python3 -m unittest discover -s tests -v`. Сравнение маршрутизации на истории: `python3 scripts/compare_live_ranking.py`. Отдельный workflow проверки кода запускает только тесты, без live-запросов и расписания. Проходимость и доходность новой версии ещё должны оцениваться на новых фактических выборах.

Отдельный замер 15/30: `benchmark-live-enrichment.yml`, только по прямому запросу через workflow_dispatch или свежий `.github/live-benchmark-request.json` в формате full-запроса. Используется тот же параллельный сбор, 16 потоков, один общий снимок и порядок 30/15/15/30, до 181 запроса. Никаких прогнозов, сохранения live-истории, реестра выборов или дневника. Если доступно меньше 30 матчей, полноценного замера 15 против 30 нет; расчёт по повторённым длительностям запросов помечается как условная проекция. Основная команда обогащает максимум 30 матчей; диагностический эксперимент не меняет рабочий лимит.

## Жёсткие границы

В активном `main` запрещено использовать или восстанавливать без отдельной команды пользователя:

- автоматический Scanner и его стратегии;
- Mining, S30 и прежние live-коллекторы;
- технические коды старых стратегий;
- forward-log и reverse-анализ прежних систем;
- старые квоты API, бюджеты запросов и расписания;
- исторические правила отбора сигналов;
- содержимое архивной ветки как действующий канон.

Прежний проект сохранён в ветке `archive/legacy-scanner-2026-10-12`. Эта ветка является только архивом и не должна читаться для текущих задач, если пользователь прямо не попросил поднять исторические данные.

## Общие правила

- Мы ищем систему и проверяем гипотезы, а не обещаем прибыль.
- В пользовательских отчётах использовать понятные русские названия.
- Для каждого матча обязательно указывать турнир.
- Актуальные данные и первоисточники имеют приоритет над памятью и старыми чатами.
- Не смешивать результаты разных правил, периодов или типов записей без явного сопоставления.
- Не менять канон или структуру дневника автоматически из-за единичного результата.
